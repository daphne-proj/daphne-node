# Migration sequence

The foundation is separate from application migration. `reference.json` records the source commit, not a passing Rust baseline. Do not treat a green TypeScript bootstrap as proof of parity.

## Current foundation slice

The TypeScript foundation now resolves public PR metadata in `@daphne/pr-review`, pins revisions and reads Git blobs in `@daphne/git-source`, exposes bounded repository tools in `@daphne/review-evidence`, and retains supplied evidence for packet assembly in `@daphne/context-engine`. The CLI composes these packages in `context inspect`, choosing retrieval policy and closing Git resources. [Architecture](../architecture.md), [ADR 0002](../adr/0002-context-engine-boundary.md) and the [context and paging guide](../../packages/context-engine/docs/context-and-paging.md) describe the boundaries and observed checks.

The experimental `split-pr` flow supplies complete pinned diff evidence and PR metadata to one continuing tool-enabled conversation. Deterministic schema and exactly-once hunk-ID validation drive repair; Git stays available until investigation ends. CLI and frozen evaluation share this flow and retain completed work on failure. See the [split README](../../packages/semantic-split/README.md) for contracts, limits and validation. This is an integration exercise, not Rust semantic-split parity; semantic quality, patch applicability and RCI/PCG migration remain separate work.

Offline Vitest tests now cover proposal validation, bounded corrections, replay, budget failures, cancellation and CLI artifact preservation. They use controlled model replies and real artifact writes; they do not establish live provider compatibility, semantic quality or Rust parity.

`apps/eval` now provides a synthetic Langfuse smoke experiment with explicit configuration, score/case completeness checks and clean telemetry finalization. It also reads and validates manually maintained split-pr gold datasets and scores saved outputs against reviewed pair labels offline. Validation and saved-output scoring make no model calls; commands cannot write into the gold cases directory. The explicit `split-pr run` command evaluates reviewed frozen cases with the shared workflow, recording native Langfuse scores/timing/provider usage and complete local trials. This is new infrastructure, not a port of Rust evaluation; scores measure agreement with the supplied labels. Broader reviewed benchmarks and model comparisons remain separate work.

The experimental `intentions` CLI investigates a public PR through `@daphne/pr-review/intentions` and `@daphne/intentions`, retaining Git for read-only model tool calls before cleanup. It prints intention cards separating actual behavior, desired outcome, motivation and potential issues, and saves pinned metadata, evidence, tool/turn history, native usage and failures in run artifacts. One writer can inspect relevant unchanged code in either revision for problems introduced, worsened or made relevant by the PR. The shared evaluator-optimizer runner validates terminal drafts deterministically and returns diagnostics to the same writer for repair; valid drafts complete without semantic reviewers. Accepted output links the exact candidate and writer turn. Runtime acceptance establishes structure and citation provenance, not factual quality or PR safety. This is a new workflow, not a Rust port. Focused conversation tests cover protocol and evidence-delivery ordering. Dedicated intentions workflow/artifact-reader tests remain deferred under repository policy; outcome/issue validators also lack dedicated regression coverage. Existing checks do not establish live explanation quality, issue discovery or reduced reviewer effort. Independent rubric v5 and gold rubric v4 assess the richer account; gold cases add draft issue expectations and false-alarm controls tied to pinned PR identity. The judge uses only source evidence from the validated run, with no separate gold source snapshot. Separate reported-issue rates and known-issue coverage are judge estimates, not total recall or measured usefulness. Follow the [manual evaluation procedure](../../apps/eval/docs/commands.md#manually-evaluate-intention-cards) before making quality claims.

## Later Rust migration sequence

1. **Capture the baseline.** Pin the Rust reference, run its relevant tests, inventory CLI/JSON/error contracts, and collect sanitized representative fixtures. Record environment, extractor versions, and timing/memory measurements. Resolve uncommitted source changes explicitly.
2. **Domain and evidence contracts.** Port identities, validated values, serialization, evidence/session types, and pure invariants with differential tests. Preserve names and observable ordering.
3. **Git and pure normalization.** Port Git source behavior and deterministic transformations. Exercise invalid revisions, unusual paths, missing files, and failure diagnostics.
4. **Extraction and indexes.** Validate tree-sitter/SCIP package choices against byte positions, language support, protobuf behavior, and fixtures. Port extraction coverage, normalization, and revision indexing in dependency order.
5. **Graph and lifecycle.** Port graph validation/building and state transitions. Test promotion, persistence compatibility, and incomplete evidence before enabling writes.
6. **Review workflows.** Port semantic grouping, review orchestration, provider adapters, and PR acquisition. Keep model calls opt-in and compare deterministic components independently of generated text.
7. **CLI and evaluation.** Extend the CLI with migrated commands, then port evaluation suites and reporting. Compare end-to-end outputs and failure exit codes against the reference. Command shells can be introduced earlier only to exercise a completed vertical slice.
8. **Cutover.** Require agreed parity, representative performance, platform/native dependency checks, and an operational rollback plan before retiring Rust paths.

For each step: name the slice and its dependencies; capture expected Rust behavior; add the target package; implement; run differential/contract checks; review; record the result. Package boundaries follow [architecture](../architecture.md), and detailed parity rules live in [parity.md](parity.md). A deliberate behavior change needs a separately recorded decision, not a silently updated golden file.
